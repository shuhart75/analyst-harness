# База продуктового знания

Проект использует `analyst-harness` для планирования, требований, прототипов, передачи в разработку, QA, план-факта и финализации релизов.

## Источники истины

- `baseline/current/` - текущее реализованное состояние системы и доменная модель.
- `features/` - изменения относительно текущего состояния, требования и срезы.
- `planning/` - входящие заметки, квартальные планы, план-факт и ретроспективы.
- `releases/` - поставленные пакеты перед переносом в текущее состояние.
- `context/source-materials/` - исходные материалы и свидетельства, но не каноническое состояние.

Корневой `features/<feature>/requirements.md` является главным документом требований. Карточки срезов, пакеты требований к клиентской и серверной части, задачи разработки и тестовые планы являются производными и должны оставаться синхронизированными с ним.

## Сквозной процесс

Репозиторий хранит продуктовое знание. Код может лежать рядом или в отдельных репозиториях. Требования не нужно копировать в кодовые репозитории как второй источник истины.

### 1. Текущее состояние

`baseline/current/` описывает уже реализованную систему:

- доменную модель и словарь;
- текущие правила и ограничения;
- текущие данные, API и интерфейсы;
- зафиксированные решения.

Новая доработка сначала живёт в `features/` как изменение. В `baseline/current/` она попадает только после финализации релиза.

### 2. Планирование

`planning/` хранит входящие заметки, квартальные планы, командирские планы, приоритеты, закрытые интервалы, состав команды и план-факт. Функциональность планируется как законченный пользовательский или системный результат. Для неё создаются ролевые плановые истории AN, BE, FE и QA, если роль участвует.

После утверждения квартальный и командирский планы не меняются. Поздно обнаруженная работа отражается на диаграмме фактического выполнения через черновики задач и фактические задачи. Это сохраняет возможность честного сравнения квартальной оценки с реальным выполнением.

### 3. Требования

`features/<feature>/requirements.md` является главным документом требований по функциональности. Он описывает изменение относительно `baseline/current/`: пользовательский результат, системное поведение, правила, изменения данных, API, интерфейсов, проверки и доработки затронутых соседних функциональностей.

Срезы в `features/<feature>/slices/<slice>/` производны от корневых требований. Они нужны для аналитической проверки целостных пользовательских сценариев, прототипов и проверок. Срезы полезны, но не являются обязательной единицей передачи в разработку.

Задачи разработки живут в `features/<feature>/tasks/`, на одном уровне с `slices/`. Это основной производный пакет для разработчика: одна задача — одна роль, один законченный технический результат и одна граница отдельного изменения. Задача может ссылаться на один срез, несколько срезов или только на разделы корневых требований.

### 4. Передача в разработку

Перед разработкой по срезу собирается пакет:

- `context-summary.md` - краткий контекст;
- `implementation-handoff.md` - передача в разработку;
- `requirements/frontend.md` и `requirements/backend.md` - требования к клиентской и серверной части, если они нужны;
- `tasks/index.md` и `tasks/*.md` - задачи разработки для передачи разработчикам;
- `execution/task-candidates.md` - дополнительный реестр черновиков задач, если проект уже использует его;
- `execution/tasks.md` - подтверждённые фактические задачи;
- `testing/test-plan.md` - проверки и покрытие.

Пакет среза не заменяет корневые требования. Если при детализации, чтении кода или проверке появляются новые правила, ограничения или влияния на соседние функциональности, сначала обновляется `features/<feature>/requirements.md`, затем пересобираются производные файлы.

### 5. Взаимодействие с кодом

Кодовые репозитории указываются в `.workflow/code-repos.json`. Идеальная модель такая:

- этот репозиторий остаётся главным источником требований и план-факта;
- кодовый репозиторий может иметь лёгкую принимающую обвязку, например папку `.workflow/dev-inbox/<task-id>/`, но она хранит только производный пакет задачи;
- пакет задачи фиксирует путь к исходным требованиям, версию репозитория требований и хеши входных файлов;
- языковая модель в режиме разработки открывает реальный код, находит затронутые модули, сравнивает фактическое устройство кода с пакетом задачи и предлагает план реализации;
- если код показывает, что требование неполное, неверно сформулировано или не учитывает существующую архитектуру, правка возвращается в требования;
- после правки требований пакет задачи обновляется, и только потом разработчик выполняет подтверждённую работу.

Если требования и код лежат в одном монорепозитории, отдельная передача в кодовый репозиторий не нужна: пакет задачи может ссылаться на соседние файлы напрямую. Если код остаётся в отдельных репозиториях, копировать туда весь набор требований не нужно - достаточно производного пакета с контрольными хешами.

### 6. Реализация и возврат факта

Рабочий цикл по задаче разработки:

1. Собрать свежий файл задачи из `features/<feature>/tasks/`.
2. Сверить задачу с реальным кодом.
3. Обновить требования, если код выявил противоречие или пропущенный хвост.
4. Подтвердить небольшие задачи с границей отдельного изменения.
5. Реализовать задачу и выполнить проверки.
6. Сверить результат с требованиями, прототипом и покрытием QA.
7. После отдельного подтверждения зафиксировать факт в `execution/tasks.md` и на диаграмме фактического выполнения.
8. В релизе собрать подтверждённое изменение.
9. После финализации релиза перенести результат в `baseline/current/`.

## Начало работы

1. Прочитать `AGENTS.md`.
2. Сформировать минимальный контекст сессии:

```bash
python .workflow/tools/harnessctl.py session-brief .
```

3. Перед широкими изменениями проверить обвязку:

```bash
python .workflow/tools/harnessctl.py doctor .
```

4. Использовать ролевые команды из `.workflow/command-cheatsheet.md`.

## Планирование

Функциональность является результатом уровня квартала. У неё может быть не более одной плановой истории на роль: `AN`, `BE`, `FE`, `QA`. Утверждённые квартальный и командирский планы неизменяемы; поздний объём работ появляется на диаграмме фактического выполнения.

Черновой план пересобирается командой:

```bash
python .workflow/tools/sync-planning-gantt.py . <YYYY-QN>
```

Утверждение выполняет только владелец проекта:

```bash
python .workflow/tools/harnessctl.py plan-approve . <YYYY-QN> --by <owner>
```

## Требования

Требования пишутся на русском языке. Английская форма допускается для кода, путей, API, БД, значений перечислений, протокольных статусов, закреплённых названий внешних систем и технических сокращений.

Проверка изменённых требований:

```bash
python .workflow/tools/harnessctl.py language-check . --feature <feature>
```

## Проверки

Базовая диагностика:

```bash
python .workflow/tools/harnessctl.py doctor .
```

Проектные сценарии проверки:

```bash
python .workflow/tools/evaluate-harness.py .
```
