# Запрос задачи на принимающей стороне

В исходной универсальной обвязке аналитик может явно поручить создание задачи
принимающей стороне. До появления реального ключа сохрани в корне выбранной
зарегистрированной поставки `analysis-task-request.json`:

```json
{
  "schema_version": 1,
  "request_id": "11111111-1111-4111-8111-111111111111",
  "provider": "sbertrek",
  "role": "AN",
  "target": "receiver",
  "delivery": "delivery-key",
  "summary": "Название аналитической работы",
  "confirmation": "Точное решение аналитика создать задачу на принимающей стороне"
}
```

Создай новый UUID для каждого запроса. Поле `key` запрещено: запрос не доказывает
создание задачи. Заголовок транспортного коммита содержит
`receiver-task/<request_id>` и смысловое описание. Для нескольких поставок нужны
все их ключи или запросы; неизменённые записи delivery-index не добавляют владельцев.
Реальная связь `analysis-task.json` имеет приоритет и проходит обычную проверку.

Исключение действует только для сохранения и переноса исходной аналитики.
Оно не разрешает публикацию `requirements-exchange/` без настоящей задачи,
не заменяет задачу квартального планирования и не снимает ограничения веток.

Принимающая Coda-обвязка разрешает задачу по `core/commit-task-resolution.md`
и использует штатный `bind-import-task` для точного ожидающего импорта.
Источник не создаёт фиктивный ключ и не переносит устаревшие команды claim/bind.
После получения подтверждённой связи действуют обычные правила схемы 2.
