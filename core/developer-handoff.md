# Передача требований в разработку

Этот договор связывает аналитическую обвязку с SDD/OpenSpec-обвязкой кодового репозитория. Пакет описывает требуемый результат, а принимающая обвязка сверяет его с выбранной ревизией кода и создаёт предложение только для фактически оставшейся дельты.

## Основной принцип

Сверка выполняется отдельно для каждого требования и сценария. Уже реализованное поведение, другое имя поля, иное техническое устройство или частичная реализация не являются ошибкой пакета и не останавливают обработку остальных пунктов.

Для каждого `REQ-*` принимающая обвязка обязана:

1. описать наблюдаемое поведение на проверенной ревизии;
2. привести проверяемые доказательства из SDD, кода, миграций или тестов;
3. сопоставить наблюдаемое поведение с требуемым результатом;
4. определить оставшуюся дельту;
5. выбрать дальнейшее действие.

## Состояния требования

| Состояние | Значение | Действие |
|---|---|---|
| `implemented-as-required` | поведение уже соответствует требованию | не включать в дельту, указать доказательства |
| `implemented-with-deviation` | реализация отличается от предположения пакета | описать отличие; если требуемый результат уже достигнут, выбрать `no-change` и вернуть обратную связь, иначе включить только однозначно требуемую коррекцию в дельту |
| `partially-implemented` | реализована только часть | зафиксировать поставленную часть, остаток включить в дельту |
| `not-implemented` | требуемое поведение отсутствует | включить в дельту |
| `blocked-product-decision` | требуемый результат нельзя определить однозначно | заблокировать только зависимые пункты и вернуть вопрос аналитику |
| `blocked-dependency` | отсутствует обязательная внешняя зависимость | заблокировать только зависимые пункты и указать зависимость |
| `not-applicable` | пункт неприменим к проверенному контуру | указать доказуемую причину |

Отличие существующей реализации от ожиданий само по себе не является блокировкой и не означает, что код нужно менять. Сначала оценивается наблюдаемый пользовательский или системный результат. Если он уже достигнут другим техническим способом, пункт получает действие `no-change`, а фактическое устройство возвращается в `baseline_feedback`. Если результат не достигнут, но целевое поведение сформулировано однозначно, принимающая обвязка создаёт дельту только для недостающего поведения и продолжает работу.

## Продолжение после сверки

После покрытия всех пунктов принимающая обвязка:

1. исключает из дельты требования, уже выполненные без необходимой продуктовой коррекции;
2. объединяет не реализованные и частично реализованные остатки в предложение SDD/OpenSpec;
3. продолжает с независимыми пунктами, даже если отдельные пункты заблокированы;
4. создаёт `proposal.md` и дельты `spec.md` для всей незаблокированной оставшейся дельты;
5. возвращает `receipt.json` с полной сверкой и перечнем сведений для обновления аналитических требований и `baseline/current/`;
6. останавливается перед `design.md`, `tasks.md` и кодом до отдельного подтверждения.

## Когда допустима остановка

Весь пакет можно остановить только когда:

- пакет повреждён, его версия не поддерживается или невозможно определить целевой контур;
- все оставшиеся пункты зависят от неразрешённого продуктового решения;
- все оставшиеся пункты зависят от отсутствующей внешней зависимости.

Если хотя бы одна независимая часть дельты однозначна и реализуема, для неё создаются предложение и спецификации. Общий статус при этом показывает наличие заблокированных пунктов, но не скрывает выполненную работу.

## Итоговые состояния пакета

| Состояние | Значение |
|---|---|
| `no-change-required` | все требования уже выполнены, дельты нет |
| `proposal-created` | для всей оставшейся дельты созданы предложение и спецификации |
| `proposal-created-with-blocked-items` | независимая дельта оформлена, отдельные пункты требуют решения или зависимости |
| `blocked` | ни один пункт оставшейся дельты нельзя продолжить |
| `rejected-package` | невозможно надёжно прочитать или направить пакет |

Состояние `baseline-mismatch` не используется как итог пакета. Расхождение с описанием текущего состояния оформляется в `baseline_feedback` квитанции, после чего аналитик обновляет `baseline/current/`, требования и производные материалы.

## Обратная связь в аналитический контур

Квитанция отдельно содержит:

- `requirement_coverage` и `scenario_coverage` без пропусков и повторов;
- `remaining_delta` для предложения SDD/OpenSpec;
- `baseline_feedback` для уточнения уже реализованного состояния;
- `requirements_feedback` для продуктовых противоречий и неясностей;
- ревизию кода, состояние рабочего дерева и структурированные доказательства;
- созданные материалы SDD и соблюдение остановки перед техническим проектированием.

Обновление аналитических требований выполняет аналитическая сторона после проверки квитанции. Разработческая сторона не переписывает продуктовый источник истины самостоятельно.
