# Бизнес-план релизов

## Размещение и назначение

Веди один `<resolved-quarter-root>/release-plan.md`. Корень квартала разрешай
через `scripts/project_layout.py`: `quarters/<quarter>` для квартальных поставок,
`planning/<quarter>` для legacy. Шаблон: `templates/planning/release-plan.template.md`.
Это бизнес-представление будущих поставок, не договор требований и не факт внедрения.
Состав, целевые даты и границы списка определяет аналитик. Фичи вне выбранной
области не добавляются автоматически. Неизвестные релизы и даты не придумывай.

## Формат

Первая таблица содержит ровно следующие столбцы в указанном порядке:

`Релиз | Плановая дата | Прогноз готовности для заказчиков | Фича | Что получат пользователи | Бизнес-ценность`

После неё допускается краткое пояснение о согласованных датах. Далее раздел
`Ключевые функции и их ценность`: для каждой фичи отдельный подраздел,
плановая дата и таблица `Ключевая функция | Ценность для бизнеса`.

- Номера допускаются только в столбце `Релиз`, где указывается номер релиза,
  а не перечень задач. В заголовках и детализации номеров быть не должно.
- Описывай возможности и пользу для пользователей на русском. Не переноси
  API, enum, имена полей, внутренние ключи и фразы «остаток вне релиза», «QA остатка».
- Польза следует из подтверждённой функции. Не придумывай автоматизацию,
  экономию времени, права или сценарии. Для частичной поставки перечисляй
  именно выпускаемые возможности, не выдавая их за полное внедрение фичи.
- Документ заканчивается после детализации последней фичи. Не добавляй разделы
  о рисках, границах, источниках, обновлении или истории. Трассировку и ограничения
  сохраняй в существующем контексте исполнения или рабочем checkpoint.

## Обязательный шаг актуализации

После каждой применённой актуализации текущих задач, включая ручные изменения,
и успешной генерации `sync-quarter-gantt.py --actual-only` агент обязан проверить
и обновить существующие списки затронутых кварталов до финального ответа и save.
Учитывай производные сдвиги других фич квартала. Отдельная просьба не требуется.
Чтение трекера без применения не запускает запись. Ошибка source/QA/generation
gate запрещает обновлять прогноз по непроверенным или частичным результатам.

1. Сопоставь строки списка с поставками и их согласованным объёмом по источникам.
   Не угадывай связи по похожему названию.
2. Проверь все строки квартала по основному полному `actual-progress`, включая
   необходимое тестирование. Альтернативный расчёт по исходным оценкам используй
   только по решению аналитика. PLAN, отменённые задачи, исторические работы и
   работы другого релиза не задают готовность этой поставки.
3. Для нескольких подтверждённых групп прогнозом служит самое позднее окончание
   необходимых работ, включая тестирование. Неизвестные даты или состав дают
   `Не определён`, а не плановую дату релиза. Причину сообщи в чате; старую дату
   не выдавай за актуальную. Закрытая разработка не доказывает готовность выпуска.
4. Обнови `Прогноз готовности для заказчиков` и дату документа. Релиз, плановую
   дату и бизнес-состав сохраняй до решения аналитика; сдвиг задачи не переносит релиз.
5. По подтверждённым изменениям состава обнови функции и ценность в обеих таблицах.
   Сохраняй ранее согласованный смысл. Завершение разработки само по себе не
   исключает функцию из будущей поставки.
6. Сверь даты с вехами Гантов и наличие детализации для каждой строки.
   Опоздания относительно цели сообщи в чате, не возвращая служебные разделы в файл.
7. Включи изменённый список в тот же проверенный набор сохранения, что исходники,
   Ганты и Confluence. `execution-update` разрешает точный `release-plan.md` только
   в кварталах зарегистрированной execution-области. Утверждённые планы защищены.

Если списка нет, создавай его по шаблону только при согласованном составе и датах;
иначе запроси недостающее решение. Если изменений нет, не переписывай файл,
отметь проверку в checkpoint. Актуализация заканчивается с проверенным списком
либо явно сообщённым блокером. Это шаг агента, не отдельное фоновое расписание.
