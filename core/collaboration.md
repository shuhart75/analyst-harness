# Совместная работа аналитиков

## Назначение

Многопользовательский режим разделяет незавершённую работу аналитиков и общую принятую версию требований в единственном рабочем репозитории `PROJECT_ROOT` (`changeswork-copy`). Отдельные форки не создаются.

- `main` содержит только принятую общую версию;
- `feature/<feature>/<analyst>` содержит первый цикл работы аналитика над
  функциональностью; если такая принятая ветка сохранена в истории, следующий цикл
  получает свободный суффикс `-2`, `-3` и создаётся от актуальной `origin/main`;
- один `features/<feature>/requirements.md` в каждый момент имеет одного ответственного редактора;
- редакция передачи в разработку создаётся только из актуальной `main` после принятия рабочей ветки человеком;
- применение входящей обратной заплаты относится только к чистой `main` без активной рабочей сессии.

Местная настройка находится в `.workspace-state/collaboration.json`, не входит ни в один Git-репозиторий и не отправляется удалённо. Её отсутствие означает незавершённую одноразовую миграцию, а не однопользовательский режим.

## Однозначный словарь команд

| Действие | Каноническая команда | Равнозначные формулировки |
|---|---|---|
| Начать работу | `начинаю работу над фичей <feature>` | `пишем требования по фиче <feature>`, `работаем с фичой <feature>`, `беру фичу <feature> в работу` |
| Сохранить | `сохрани работу` | `сохрани`, `зафиксируй изменения`, `закоммить изменения`, `сделай коммит` |
| Обновить рабочую ветку | `обнови мою ветку` | `обнови`, `синкани`, `подтяни изменения`, `синкани мою ветку` |
| Передать на проверку | `требования готовы к объединению` | `отправь требования на проверку`, `подготовь требования к слиянию`, `отправь ветку на слияние` |
| Завершить после принятия | `запрос на слияние принят` | `запрос принят`, `ветка принята в main`, `слияние выполнено` |
| Передать разработке | `сформируй пакет для разработки` | `отправь требования в разработку`, `передай требования разработчикам`, `передай разрабам` |
| Принять обратную заплату | `влей обратный дифф` | `прими изменения из documents`, `примени обратную заплату`, `влей изменения из documents` |

Контекстное различие обязательно:

- короткое `синкани` при активной рабочей ветке обновляет эту ветку из `origin/main`;
- вне активной рабочей ветки голые `обнови` или `синкани` без объекта неоднозначны: LLM задаёт один вопрос и ничего не изменяет;
- команда принятия обратной заплаты не обновляет рабочую ветку: она требует завершённую сессию совместной работы и выполняет полный договор `core/reverse-patch.md` на `main`.

## Процесс аналитика

1. До чтения требований функциональности LLM выполняет `workspace.py bootstrap` и `collaboration.py status`.
2. Если получено `migration-required`, LLM запрашивает короткий идентификатор аналитика и выполняет одноразовую миграцию. Существующую локальную работу нельзя приписывать функциональности автоматически.
3. LLM разрешает существующий идентификатор функциональности и вызывает `collaboration.py start`. Новая ветка создаётся от актуальной `origin/main`.
4. Во время обычной работы изменяется корневой `features/<feature>/requirements.md`. Срезы и редакция передачи не создаются и не обновляются.
5. По команде сохранения LLM проверяет изменения и передаёт `collaboration.py save` полный точный список путей. Создаётся один смысловой коммит и отправляется только рабочая ветка.
6. По команде обновления `origin/main` объединяется с рабочей веткой. Перед изменением создаётся защитный снимок. Конфликт сохраняет стороны и требует решений по одному пути.
7. По команде готовности LLM полностью проверяет требования, сохраняет остаток, обновляет ветку, повторяет проверки и вызывает `collaboration.py submit`. Команда отправляет ветку, но не создаёт и не принимает запрос на слияние.
8. После принятия ветки человеком `collaboration.py finish` доказывает включение её коммита в `origin/main`, безопасно обновляет локальную `main` и закрывает рабочую сессию.
9. Перед аудитом и передачей в разработку обязателен `collaboration.py require-main-for-delivery`. После успешной проверки LLM проводит аудит требований, показывает отчёт аналитику и ждёт явного подтверждения аудита и отправки. Только затем создаётся новая редакция передачи из `requirements.md` и `manifest.json`; срезы и предварительные задачи не создаются.
10. Входящая обратная заплата принимается только через `reverse_patch.py discover`, `inspect`, `apply` после подтверждения чистой `main` и отсутствия активной рабочей сессии.

## Ограничения

- Тема и тело любого коммита содержат только смысловое описание изменения. Номера задач и идентификаторы трекеров запрещены также в автоматически создаваемых сообщениях слияния и squash. `collaboration.py save` проверяет сообщение до индексирования файлов, а установленный bootstrap `commit-msg` hook блокирует прямые Git-коммиты. Обход hook запрещён.
- В одной установке одновременно активна только одна функциональность. Параллельная работа того же аналитика требует отдельной рабочей области.
- Два аналитика не редактируют один `requirements.md` независимо.
- Прямая отправка рабочей команды в `main`, автоматическое принятие запроса на слияние, `rebase`, `reset`, принудительная отправка и широкое индексирование запрещены.
- Рабочая ветка не меняет корневую обвязку и не принимает обратную заплату.
- Аудит для передачи, редакция передачи и её служебное описание не создаются в непринятой рабочей ветке.

## Одноразовая миграция

1. Выполнить bootstrap и `collaboration.py status`.
2. Если в `PROJECT_ROOT` уже есть `MERGE_HEAD`, остановиться и разрешить конфликт по одному пути; обвязка не отменяет чужое слияние.
3. Запросить короткий постоянный идентификатор аналитика: строчные латинские буквы, цифры и дефисы.
4. Выполнить `collaboration.py migrate --analyst <id>`.
5. Чистая `main`, совпадающая с `origin/main`, включается без изменения проектного дерева.
6. При локальной работе сначала запросить одну функциональность и повторить миграцию с `--feature <feature>`; автоматического коммита и push нет.
7. После миграции проверить: текущая ветка `main`, `active_work = null`, рабочее дерево чистое.

Миграция не удаляет ветки, не переписывает историю, не создаёт коммиты из незакоммиченных файлов и не выполняет rebase, reset или force push.
