# Приём обратной заплаты

Этот договор применяется на машине, где настроенный репозиторий роли `analytics` является рабочим репозиторием, в который нужно вернуть проверенные изменения из другой аналитической рабочей области.

## Вход и результат

Вход состоит из неизменяемой пары:

- `reverse-diff-<artifact-id>.json` со схемой 2;
- `reverse-diff-<artifact-id>.patch` с указанной в JSON контрольной суммой SHA-256.

Программа ищет пары в игнорируемом каталоге `HARNESS_ROOT/reverse-patch-inbox/` и в `~/Downloads`. Пользователь не указывает пути. Если найдено несколько разных `artifact_id`, LLM показывает их и просит выбрать только один идентификатор.

Успешное применение создаёт ровно один интеграционный коммит в `main`, отправляет его в `origin/main` и записывает местную квитанцию в `HARNESS_ROOT/reverse-patch-receipts/`. Оба служебных каталога игнорируются Git и не должны попадать в коммиты обвязки.

## Обязательный порядок LLM

Для команд `прими изменения из documents`, `примени обратную заплату`, `влей обратный дифф`, `влей изменения из documents` и близких по смыслу формулировок:

1. Выполни `python3 HARNESS_ROOT/scripts/reverse_patch.py discover`.
2. Если подходящей пары нет, сообщи причины из поля `invalid`; не предлагай применить непроверенный файл.
3. Если пара одна, используй её `artifact_id` без дополнительного вопроса. Если пар несколько, попроси пользователя выбрать только `artifact_id`.
4. Выполни `python3 HARNESS_ROOT/scripts/reverse_patch.py inspect --artifact-id <id>`. Команда в отдельных временных индексе и хранилище объектов проверяет применимость, пробельное оформление и точное воспроизведение целевого дерева, не изменяя рабочий репозиторий и его `.git/objects`. Кратко сообщи исходный коммит, целевое дерево и состав функциональностей.
5. Выполни `python3 HARNESS_ROOT/scripts/reverse_patch.py apply --artifact-id <id>`.
6. Сообщи итоговый статус, интеграционный коммит и путь к квитанции. Не объявляй репозитории совпадающими только по факту создания заплаты; совпадение подтверждается целевым деревом после применения.

Команда является разрешением на весь описанный цикл, включая защищённый `git pull --ff-only`, один коммит и обычный push. Отдельное подтверждение перед этими шагами не требуется.

## Защитные условия

Применение разрешено только при одновременном выполнении условий:

- JSON имеет схему 2 и признаки `verified=true`, `tree_verified=true`, `content_policy_verified=true`; новые пары также содержат `diff_check_verified=true`, а старые пары схемы 2 без этого поля проходят ту же независимую проверку на принимающей стороне;
- SHA-256 файла заплаты совпадает с квитанцией;
- рабочий репозиторий чист, находится в ветке `main` и не содержит незавершённого слияния;
- `git pull --ff-only origin main` выполнен успешно;
- текущие коммит и дерево точно совпадают с `source_commit` и `source_tree`;
- временное применение заплаты воспроизводит `analytics_tree`;
- фактически изменённые пути точно совпадают с `changed_paths`;
- после коммита итоговое дерево равно `analytics_tree`.

Если `source/main` ушла вперёд, старую заплату нельзя приспосабливать вручную: требуется снова синхронизировать исходную аналитическую рабочую область и выпустить новую пару. При ошибке до коммита программа возвращает индекс и рабочее дерево в исходное состояние.

## Повторный запуск

- Если интеграционный коммит уже находится в `origin/main`, команда возвращает `already-applied` и не создаёт второй коммит.
- Если коммит создан, но push ранее не прошёл, квитанция имеет статус `committed-not-pushed`; повторный запуск отправляет тот же коммит.
- Если целевое дерево уже оказалось в `origin/main` другим корректным способом, команда записывает `observed-already-integrated` и не создаёт коммит.

Запрещены `reset`, `rebase`, force push, ручное изменение заплаты, широкое индексирование через `git add -A` или `git add .` и автоматический выбор между несколькими `artifact_id`.
