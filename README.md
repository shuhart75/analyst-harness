# Универсальная аналитическая обвязка

`analyst-harness` создаёт рабочую область для долгоживущего продуктового знания: текущего состояния системы, планов, требований, прототипов, пакетов передачи, фактического выполнения и выпусков. Обвязка отделена от проектных данных и от кода.

## Архитектура

После настройки в одном каталоге находятся независимые Git-репозитории:

```text
analyst-harness/
├── AGENTS.md
├── core/
├── modes/
├── scripts/
├── skills/
├── templates/
├── .analyst-workspace.json       # местная настройка, не версионируется
├── .workspace-state/             # режимы и состояния циклов, не версионируются
├── reverse-patch-inbox/          # входящие пары обратного обмена, не версионируются
├── reverse-patch-receipts/       # квитанции применения, не версионируются
├── analyst-workspace.code-workspace
├── analytical-project/           # роль analytics; имя можно изменить
│   └── AGENTS.md                 # местная игнорируемая точка входа
└── code/                         # необязательный репозиторий, имя можно изменить
```

Корневая обвязка хранит правила, режимы, инструменты и шаблоны. Аналитический репозиторий хранит только проектные данные. Кодовый репозиторий подключается только для ограниченного чтения и может отсутствовать.

Назначение определяется ролью, а не именем каталога. Репозиторий роли `analytics` является `PROJECT_ROOT`; необязательный репозиторий роли `code` доступен строго только для чтения за исключением первоначального создания или клонирования, защищённого `git pull --ff-only` и изолированной публикации в заранее созданный разработчиками `requirements-exchange/**`. Публикация выполняется через временную копию, не изменяет обычный клон кода и при любой недоступности использует резервный каталог в роли `analytics`.

В отслеживаемом Git-дереве роли `analytics` запрещены копии:

- `.workflow/`;
- `.vscode/`;
- `AGENTS.md` аналитической обвязки.

Программа развёртывания создаёт в корне роли `analytics` местный `AGENTS.md`, который ведёт LLM к корневой обвязке. Он исключён через `.git/info/exclude`, не входит в Git и не загрязняет рабочее дерево. Формальный договор принимающей SDD создаётся отдельно в корне `requirements-exchange/AGENTS.md`.

Тот же местный файл исключений защищает `.codex/`, `.gigacode/`, `.gigaide/`, `.idea/`, `GIGACODE.md`, `*.iml` и `*.orig`. Уже отслеживаемые локальные файлы не скрываются и должны удаляться из Git точечно; широкие команды `git add -A` и `git add .` для такой очистки запрещены.

## Первый запуск

Клонируйте `analyst-harness` и запустите LLM в его корне. Если `.analyst-workspace.json` отсутствует, LLM должна задать вопросы последовательно, по одному:

1. Аналитический репозиторий клонировать или создать?
2. Если клонировать, какой адрес использовать?
3. Кодовый репозиторий клонировать, создать или не подключать?
4. Если клонировать, какой адрес использовать?

Адреса не имеют значений по умолчанию и не угадываются. Каталоги по умолчанию: `analytical-project/` и `code/`.

Пример для двух существующих репозиториев:

```bash
python3 scripts/workspace.py configure \
  --analytical-mode clone --analytical-url <url> \
  --code-mode clone --code-url <url>
python3 scripts/workspace.py bootstrap
```

Новый аналитический репозиторий без кода:

```bash
python3 scripts/workspace.py configure \
  --analytical-mode create \
  --code-mode skip
python3 scripts/workspace.py bootstrap
```

Поддерживаемые сочетания:

| Аналитический репозиторий | Кодовый репозиторий | Результат |
|---|---|---|
| клонировать | клонировать | два существующих независимых репозитория |
| клонировать | создать | существующее знание и новый локальный кодовый репозиторий |
| создать | клонировать | новый аналитический проект и существующий код |
| создать | создать | два новых независимых Git-репозитория |
| клонировать или создать | не подключать | аналитическая работа без исследования кода |

`bootstrap` безопасно повторяется: проверяет сохранённый выбор, репозитории и рабочую область. Он не задаёт вопросы повторно, не копирует отслеживаемую обвязку в аналитический проект и обновляет местную игнорируемую точку входа.

Состояние настройки:

```bash
python3 scripts/workspace.py status
```

Перенастройка требует явного `configure --force`. Обвязка не удаляет старые каталоги и не переносит данные автоматически.

## Откуда запускать LLM

После первого `bootstrap` аналитик может запускать LLM:

- из корня `analyst-harness`;
- непосредственно из настроенного репозитория роли `analytics`.

В обоих случаях модель обязана определить `HARNESS_ROOT`, получить `PROJECT_ROOT` командой `python3 scripts/workspace.py project-root` и записывать `baseline/`, `context/`, `planning/`, `features/` и `releases/` только в `PROJECT_ROOT`. При запуске из `analytics` местный игнорируемый `AGENTS.md` содержит абсолютные `HARNESS_ROOT`, `PROJECT_ROOT` и, при наличии, `CODE_ROOT` этой машины. Поэтому маршрутизация не зависит ни от имени репозитория, ни от текущего вложенного каталога, а исследование роли `code` выполняется через единую корневую обвязку.

## Граница ответственности

### В обвязке

- `AGENTS.md` - обязательный договор LLM;
- `core/` - правила качества, контекста, исследования, передачи и циклов;
- `modes/` - режимы планирования, требований, прототипирования, фактического выполнения и завершения выпуска;
- `scripts/` - проверки и генераторы;
- `templates/` - шаблоны документов и пакетов;
- `skills/` - повторяемые циклы;
- `.workspace-state/active-mode.md` - текущий режим;
- `.workspace-state/runs/` - состояния выполняемых циклов;
- `.workspace-state/code-repos.json` - местный реестр необязательного кода.

### В аналитическом репозитории

```text
analytical-project/
├── README.md
├── baseline/
│   ├── current/
│   └── versions/
├── context/
│   ├── source-materials/
│   ├── current-system/
│   ├── change-requests/
│   ├── project-rules/
│   ├── evals/
│   └── analysis-log.md
├── planning/
│   ├── team.md
│   ├── consistency-backlog.md
│   ├── approved-plans/
│   └── <YYYY-QN>/
├── features/
├── requirements-exchange/       # резервное размещение, создаётся при необходимости
└── releases/
```

Проектные правила, состав команды, утверждённые планы и журнал решений версионируются вместе с проектом. Текущий режим, временные сводки и состояния циклов относятся к конкретной машине и остаются в обвязке.

## Сквозной процесс

### 1. Текущее состояние

`baseline/current/` описывает только подтверждённое реализованное поведение: доменную модель, правила, данные, API, интерфейсы, решения и ограничения. Будущая работа живёт в `features/` как изменение относительно текущего состояния.

Исходные материалы в `context/source-materials/` являются доказательствами, но не заменяют обработанное текущее состояние.

### 2. Планирование

Квартальные работы группируются по функциональностям. Одна функциональность - законченный пользовательский или системный результат. Для неё создаётся не более одной плановой истории каждой участвующей роли: `AN`, `BE`, `FE`, `QA`.

Правила по умолчанию:

- приоритетные функциональности начинаются раньше;
- загрузка доступных ресурсов максимизируется, но не превышает 100 процентов;
- трудоёмкость роли распределяется по команде с учётом ограничений параллельности;
- коэффициенты: `AN = 0.80`, `BE = 0.70`, `FE = 0.65`, `QA = 0.80`;
- персональные коэффициенты и закрытые интервалы задаются в `planning/team.md`;
- клиентская работа начинается не раньше чем через три рабочих дня после начала связанной серверной работы;
- запас риска не менее 20 процентов учитывается в командирском плане, но не показывается отдельной полосой;
- основной артефакт - диаграмма Ганта PlantUML;
- план утверждает только пользователь-владелец;
- утверждённые квартальный и командирский планы неизменяемы.

Поздно обнаруженная работа отражается в фактическом выполнении. По итогам квартала оценки сравниваются с фактом для последующей калибровки коэффициентов.

### Совместная работа над функциональностью

Требования изменяются только в зарегистрированной ветке `feature/<feature>/<analyst>`.
Если ветка предыдущего принятого цикла ещё хранится локально или на сервере, обвязка
создаёт новую от актуальной `origin/main` с суффиксом `-2`, затем `-3`; удалять
старую ветку для повторной работы не требуется. LLM сама выполняет защищённые
программы, пользователь работает короткими командами:

1. `начинаю работу над фичей <feature>` — обновить сведения об `origin/main`, создать или продолжить рабочую ветку и зарегистрировать владельца;
2. `сохрани работу` — проверить и зафиксировать только точные изменённые пути, затем отправить рабочую ветку;
3. `обнови мою ветку` — безопасно объединить актуальную `origin/main` с рабочей веткой без rebase и force push;
4. `требования готовы к объединению` — повторить проверки, сохранить остаток и вернуть ссылку на форму запроса на слияние; сам запрос создаёт и принимает человек;
5. `запрос на слияние принят` — доказать, что отправленный коммит содержится в `origin/main`, обновить местную `main` и закрыть сессию.

Пакет для разработки создаётся только из чистой актуальной `main` после завершения этой последовательности. В одной установке одновременно ведётся одна функциональность; параллельная работа требует отдельной рабочей области.

При первом запуске версии с совместной работой выполняется одноразовая миграция:

1. LLM повторяет `bootstrap` и проверяет `collaboration.py status`.
2. Если состояние равно `migration-required`, LLM просит короткий постоянный идентификатор аналитика.
3. При чистой актуальной `main` выполняется `collaboration.py migrate --analyst <id>`; проектные файлы и история не меняются.
4. Если уже есть отдельные коммиты или незакоммиченные изменения, обвязка ничего не переносит автоматически и просит указать одну функциональность. Затем выполняется миграция с `--feature <feature>`, а вся существующая работа остаётся в созданной рабочей ветке без автоматического коммита и отправки.
5. После чистой миграции LLM начинает работу только по явной команде аналитика. После миграции с сохранением работы сначала проверяются и сохраняются точные изменённые пути.

Миграция не удаляет ветки, не переписывает историю, не выполняет `rebase`, `reset`, принудительную отправку и широкое индексирование.

### 3. Требования

`features/<feature>/requirements.md` - единственный авторский документ требований функциональности. Он оформляется как компактная спецификация в духе SDD, но остаётся бизнес-контрактом, а не техническим `spec.md`. ISO-подобный и прежний многораздельный последовательный форматы больше не используются для новых передач.

При явно порученной миграции прежний документ можно один раз переименовать в `requirements_iso.md`. Это неизменяемая архивная копия: она не является источником требований, не проходит проверки живого документа и не передаётся разработчикам.

Обязательные свойства:

- назначение, законченный результат и явные границы;
- правила `REQ-*` в естественном порядке процесса;
- хотя бы один вложенный сценарий с ключевыми словами `Когда` и `Тогда` у каждого правила;
- необязательное связное описание процесса, данных и состояний только когда оно помогает чтению;
- трассировка по устойчивым `REQ-*` без обязательной таблицы, повторяющей полный текст;
- обязательный раздел влияния на соседние функциональности, включая необходимые доработки;
- явная подчистка устаревшего поведения и неотслеженных хвостов;
- отсутствие противоречий с текущим состоянием и соседними требованиями;
- наглядные диаграммы только в PlantUML, дополняющие текст, но не вводящие самостоятельных правил;
- русский язык с английским только для кода, путей, API, полей, статусов, форматов и необходимых специальных терминов.

Каждая фраза дополнительно проходит договор контролируемых формулировок из
`core/requirements-wording.md`. Количества и области действия задаются явно;
`Когда` содержит конкретное состояние и событие, а `Тогда` — наблюдаемый результат
без повторения `система должна`. Команды `проверь формулировки требований`,
`проверь однозначность требований` и `найди плохо составленные требования`
выполняют эту проверку без создания редакции передачи.

Пока аналитик прорабатывает функциональность, LLM изменяет только корневой `requirements.md` как документ требований. Срезы, отдельные требования клиентской и серверной частей, предварительные задачи разработки и редакции передачи не создаются.

Сам `requirements.md` не содержит поля `Статус`: оно создало бы неоднозначность с
исполняемой статусной моделью. Авторская готовность и аудит хранятся в
`features/<feature>/requirements-state.json`, а состояние передачи конкретной
неизменяемой редакции — в `manifest.json` каталога обмена. Источник каждой правки
фиксируется как `analyst` или `developer-result`. Изменение по принятому результату
разработки не создаёт и не предлагает новую редакцию. После инициативного изменения
уже переданных требований LLM один раз предлагает новую редакцию; отказ действует
до следующей явной команды передачи.

Служебные переходы, которые LLM выполняет сама, где `<project>` разрешается через роль `analytics`:

```bash
python3 scripts/requirementsctl.py status <project> <feature>
python3 scripts/requirementsctl.py record-change <project> <feature> --origin analyst
python3 scripts/requirementsctl.py record-change <project> <feature> --origin developer-result --return-id <id>
python3 scripts/requirementsctl.py mark-offered <project> <feature>
python3 scripts/requirementsctl.py decline-revision <project> <feature>
python3 scripts/requirementsctl.py begin-preparation <project> <feature>
python3 scripts/requirementsctl.py record-audit <project> <feature> --finding-count <N> --accepted-risk-count <N> --blocking-finding-count <N> --summary <итог>
python3 scripts/requirementsctl.py confirm-audit <project> <feature>
python3 scripts/requirementsctl.py mark-published <project> <feature> --manifest <путь> --revision <N> --destination-role <analytics|code>
```

Аналитику эти команды помнить не требуется. Файл состояния переносит решение между задачами LLM и машинами. Устаревший `handoffctl.py` не используется для новых передач.

Перед изменением существующей функциональности LLM проверяет состояние. Если живые требования расходятся с последней отправленной редакцией, обвязка требует сначала классифицировать расхождение. LLM не угадывает источник, а задаёт один вопрос: это инициативная правка или принятый результат разработки.

### 4. Исследование кода

Если код подключён, путь и контуры находятся в `.workspace-state/code-repos.json`. Пользователь может сказать `сходи в код`, `посмотри в коде` или `проверь по коду` без указания пути.

LLM не читает репозиторий целиком:

1. фиксирует ветку, коммит и чистоту рабочего дерева;
2. выбирает один контур;
3. читает его локальные инструкции;
4. ищет точные сущности, поля, маршруты или символы;
5. открывает найденные модули и соседние проверки;
6. сохраняет краткие доказательства с относительными путями;
7. подтверждает, что код за время исследования не изменился.

Низкоуровневые команды, где `<project>` берётся из `.analyst-workspace.json`:

```bash
python3 scripts/code-inspect.py doctor <project>
python3 scripts/code-inspect.py locate <project> '<строка>' --contour <contour>
python3 scripts/code-inspect.py begin <project> --contour <contour> --feature <feature> --query '<цель>'
python3 scripts/code-inspect.py verify <файл-состояния>
```

Если код не подключён, планирование и требования продолжаются. Технические предположения отмечаются как непроверенные и повторно проверяются принимающей SDD.

### 5. Передача разработчикам

Команда `сформируй пакет для разработки` и её синонимы запускают обязательный аудит, а не немедленную публикацию. Полный алгоритм закреплён в `core/requirements-audit.md`.

Аудит выполняется в три уровня:

1. каждое `REQ-*` отдельно проверяется на один смысл, однозначность и проверяемость;
2. весь набор проверяется как единая система ролей, действий, состояний, данных, сценариев, зависимостей и влияний;
3. проверяется готовность к передаче: формат, покрытие сценариями, трассировка, язык, PlantUML, хвосты и контрольная сумма.

На втором уровне LLM обязана рассуждать между требованиями, а не только читать их по очереди. После каждого ответа аналитика повторно проверяются затронутые связи, а после последнего исправления все три уровня выполняются заново по полному документу.

Исправления без изменения смысла вносятся автоматически. При содержательной неопределённости LLM показывает связанные места, проблему, последствия и допустимые варианты, затем задаёт аналитику один вопрос и ничего не придумывает. Итоговый отчёт содержит метод аудита, состояние трёх уровней, все замечания и решения, исправления, принятые риски, блокировки, предположения и контрольную сумму. Затем задаётся прямой вопрос: `Подтверждаете результат аудита и отправку требований в разработку?`

До явного положительного ответа редакция обмена не создаётся. Исходная команда передачи не считается подтверждением результата аудита. Подтверждение привязано к контрольной сумме `requirements.md`; любое последующее изменение требует нового аудита. После подтверждения редакция сразу публикуется в состоянии `sent`, без промежуточного пакета `ready`.

Каноническая структура:

```text
requirements-exchange/
├── README.md
├── AGENTS.md
└── <feature>/
    ├── manifest.json
    └── revisions/
        └── 001/
            ├── requirements.md
            └── returns/
                ├── tasks.md
                ├── tasks/
                │   └── <task-id>.md
                └── summary.md
```

Вход функциональности состоит только из `manifest.json` и одной неизменяемой редакции `requirements.md`. Переданный файл является бизнес-контрактом. Разработческая SDD не копирует его целиком в локальный `spec.md`: она сверяет требования с кодом, выделяет техническую дельту каждого контура и создаёт собственные `proposal/spec/design/tasks` либо их местные аналоги. Каталог `returns/` создаётся при появлении первого результата. ZIP не создаётся автоматически и запрещён внутри репозитория.

Место выбирается автоматически:

1. если роль `code` настроена, обвязка создаёт временную копию её актуальной ветки;
2. если разработчики заранее создали в корне `requirements-exchange/`, обвязка меняет только этот путь, проверяет состав, создаёт коммит и отправляет его в ту же ветку;
3. обычный клон роли `code` остаётся на прежних ветке, коммите и состоянии;
4. если роли `code`, каталога, чтения или права отправки нет, создаётся `PROJECT_ROOT/requirements-exchange/`;
5. итог сообщает фактическую роль, редакцию и место: удалённую ветку с путём либо абсолютный резервный путь.

### 6. Декомпозиция, реализация и тестирование

Разработчики определяют декомпозицию в своём процессе. В `returns/tasks.md` SDD записывает только уже согласованный перечень задач:

- устойчивый идентификатор и название;
- ровно один контур и содержание;
- связанные `REQ-*`;
- локальное изменение SDD и созданные технические материалы;
- зависимости;
- необязательную оценку;
- необязательный ключ Jira.

Клиентская и серверная работа не смешиваются в одной задаче; одно требование может быть связано с несколькими задачами разных контуров. Аналитик не подтверждает `tasks.md`, а его обработка не блокирует разработку. По мере выполнения задач SDD создаёт `returns/tasks/<task-id>.md`, где фиксирует локальное изменение SDD, существовавшее поведение, выполненную работу, отличия, остаток, коммиты, пути и проверки. Уже реализованное, иначе реализованное или частично реализованное правило не останавливает независимую работу.

Итоговый `returns/summary.md` покрывает каждый `REQ-*` активной редакции и показывает фактическое состояние, отличия, оставшуюся работу и доказательства. Аналитик отдельно решает, что перенести в `baseline/current/`, что уточнить в требованиях, а что отменить, отложить или перенести. Историческая входная редакция и утверждённый план не переписываются. Изменение требований по принятому результату не создаёт новую редакцию; отдельная передача появляется только по явному решению аналитика.

Команда `проверь результаты разработки` запускает `requirements-exchange.py scan`. По умолчанию показываются новые результаты текущего аналитика; просмотр всех владельцев требует явной команды. Новизна определяется по пути и контрольной сумме, а принятое решение регистрируется в `features/<feature>/development-results-state.json`.

### 7. Чтение SberTrek и Jira

Команды `прочитай задачи из трекеров`, `проверь задачи в трекерах`,
`сверь SberTrek и Jira` и `покажи текущее состояние по трекерам` запускают
безопасную сверку без изменения трекеров и аналитического репозитория.

При незавершённой первичной настройке это не команда немедленного поиска. LLM
задаёт ровно один вопрос дословно, без вступления, примеров и подсказок, сохраняет
ответ и последовательно задаёт следующие. Конечные и исключающие статусы
настраиваются отдельно для SberTrek и Jira.
До завершения настройки она не читает задачи и не показывает предварительную
сводку. `config-status` запускается отдельно, без `head`, `tail`, `grep`, `jq` и
других фильтров; код `3` и `must_stop: true` запрещают любые MCP-вызовы. Чтение
выполняет только главный агент после `begin`, а итог показывается только после
успешного `reconcile` с тем же `run_id`, `workflow_complete: true` и
`final_response_allowed: true`. Ошибка `reconcile` запрещает ручную сводку по уже
прочитанным данным.

Процесс:

1. При первом запуске по одному уточняются проекты, типы единиц разработки и
   конечные и исключающие статусы. Встреченные account id затем последовательно
   связываются только с `team_id` из `planning/team.md`; роль выводится из префикса
   `AN`, `BE`, `FE` или `QA`. Короткие формы `A`, `B`, `F`, `Q` равнозначны.
2. После готовой настройки LLM находит MCP-инструменты SberTrek и Jira по возможностям, а не по имени сервера.
3. Каждый известный или найденный ключ напрямую читается под тем же точным ключом
   и в SberTrek, и в Jira. Пара образуется только при полном равенстве ключей;
   `issue_key`, `counterpart_key`, названия и ручные связи на сопоставление не
   влияют. Jira заполняет отсутствующие оценки и другие поля совпавшей пары и
   дополняет её историю.
   Эпик, исполнитель и оценка склеиваются независимо: заполненное значение
   SberTrek имеет приоритет, а Jira используется только для отсутствующего поля.
   При конфликте сохраняется SberTrek и показывается расхождение. Оценка
   нормализуется в `story-points`; для процесса действует `1 SP = 1 человекодень`.
4. После каждого MCP-ответа LLM сохраняет данные штатными командами
   `snapshot-metadata`, `snapshot-issue`, `snapshot-not-found`, `snapshot-history`
   и `snapshot-collection`; утверждения полноты содержат доказательство MCP-вызова,
   а `run-status` показывает незаполненные части. Для каждой задачи отдельно
   фиксируется, было ли получено значение исполнителя, оценки, эпика и релизов,
   подтверждено их отсутствие или MCP не вернул поле. Полная история перечисляет
   все ключи задач, для которых она реально запрашивалась. Задача записывается
   только после прямого чтения по ключу с evidence этого вызова; поисковой выдачи
   недостаточно. `cross_provider_lookup` вычисляет evidence и проверенные ключи
   автоматически.
5. Разные заполненные значения показываются как конфликт. SberTrek остаётся
   эффективным источником.
6. Для каждого найденного эпика читается ограниченный список остальных задач.
   Прямо связанные с функциональностью задачи предлагаются к включению; по
   сомнительным задачам LLM задаёт аналитику один вопрос.
7. Один набор показывается отдельно по эпикам и по релизам. Отсутствующие на
   actual-progress релизы показываются как предложения.
8. Завершение разработки определяется по явному статусу либо по подтверждённому
   историей переназначению с участника роли `developer` на участника другой роли.
   Правило действует для настроенных типов, включая Story, если она является
   единицей разработки проекта.

Первый запуск полностью управляется коротким пользовательским промптом. Внутри LLM
выполняет `trackerctl.py config-status`, задаёт недостающие вопросы строго по одному
и подтверждает настройку до `begin`. `begin` создаёт шаблоны снимков с проверяемым
   паспортом чтения истории, связей, точных ключей в обоих провайдерах, эпиков и
   релизов. Неполная настройка, состояние `pending`, незакрытый seed, неизвестный
   участник или непроверенный в одном из провайдеров точный ключ блокируют полный
   `reconcile`;
недоступная возможность MCP явно попадает в ограничения только после реальной
неуспешной попытки вызова.
Прямые результаты MCP не показываются как итог: сначала `run-status` должен вернуть
`tracker-run-ready`, затем `reconcile --run-id ...` формирует проверенный отчёт.
После этого `result-status --run-id ...` и повторный `run-status --run-id ...`
возвращают один сохранённый официальный статус; модель не собирает его вручную.
Каждый исходный seed-ключ ссылается на аналитический источник и обязан завершиться
найденной задачей своего провайдера либо доказанным `not-found`; результат
текстового поиска без такого источника остаётся кандидатом и не выдаётся за
известную задачу. Seed имеет вид `PROJECT-123`; если известных ключей нет, список
остаётся пустым, а фиктивный `FEATURE` запрещён. SberTrek/Jira сопоставляются
исключительно по точному ключу.

Если сверка остановлена на вопросе о `team_id`, `reconcile`, `run-status` и
`result-status` запрещают сводку и возвращают один и тот же обязательный вопрос.

Итоговые количества и ограничения берутся непосредственно из `trackerctl` и
`report.md`. LLM не пересчитывает их вручную и не может сообщить об отсутствии
ограничений при неполном сборе.

Старый пустой конфиг первой версии распознаётся автоматически и возвращается в
состояние незавершённой настройки; фиктивный тип `development-task` не наследуется.
Старые свободные маппинги участников очищаются один раз и повторно собираются через
обязательные вопросы текущего запуска.

Снимки и отчёты находятся только в игнорируемой
`.workspace-state/tracker-runs/`. Включение найденных задач и релизов в
actual-progress будет отдельной подтверждаемой операцией.


## Возврат изменений в исходный аналитический репозиторий

Если аналитическая работа велась в отдельном репозитории и из неё получена проверенная обратная заплата, `analyst-harness` может безопасно вернуть результат в настроенный рабочий репозиторий. Полный путь обмена выглядит так:

```text
отдельный аналитический репозиторий
-> reverse-diff-<artifact-id>.json + reverse-diff-<artifact-id>.patch
-> рабочий репозиторий роли analytics
-> один интеграционный коммит в main
-> origin/main
-> квитанция применения
```

На принимающей машине настройте рабочий исходный репозиторий как роль `analytics`. Пару `JSON + patch` можно положить в `reverse-patch-inbox/` или оставить в `~/Downloads`; оба файла должны находиться рядом. Затем достаточно написать LLM одну из команд:

```text
прими изменения из documents
примени обратную заплату
влей обратный дифф
влей изменения из documents
```

LLM сама выполняет `discover`, `inspect` и `apply`. Пути у пользователя не запрашиваются. `inspect` проверяет заплату в отдельных временных индексе и хранилище объектов: применимость, пробельное оформление и точное воспроизведение целевого дерева. Рабочее дерево, индекс проекта и `.git/objects` при этом не меняются. Если проверка не пройдена, `apply` не выполняется, транспортная пара не редактируется и требуется новая пара, сформированная после исправления исходного `analytics`. Если найдена одна проверенная пара, она применяется без дополнительного вопроса. Если найдено несколько разных идентификаторов, пользователь выбирает только `artifact_id`; автоматический выбор запрещён. Старые пары схемы 2 без поля `diff_check_verified` остаются совместимыми, поскольку принимающая сторона выполняет эту проверку самостоятельно.

Перед изменением репозитория программа проверяет схему и признаки проверки JSON, SHA-256 заплаты, чистоту рабочей копии, ветку `main`, отсутствие незавершённого слияния, выполняет `git pull --ff-only origin main` и требует точного совпадения текущего коммита и дерева с исходной точкой заплаты. Затем заплата сначала применяется во временный индекс: полученное дерево обязано совпасть с целевым деревом аналитического репозитория. При настоящем применении дополнительно сверяется полный список путей и `git diff --check`.

При успехе создаётся ровно один интеграционный коммит и выполняется обычный push в `origin/main`. Квитанция записывается в игнорируемый каталог `reverse-patch-receipts/` и содержит итоговые коммит и дерево. Повторный запуск не создаёт второй коммит. Если первый push не прошёл, статус `committed-not-pushed` позволяет следующему запуску отправить тот же коммит. Если `source/main` уже ушла вперёд, применение блокируется: нужно сформировать новую заплату от актуального исходного состояния.

Программа не использует `reset`, `rebase`, force push, `git add -A` или `git add .`. Ошибка до создания коммита возвращает индекс и рабочее дерево в исходное состояние. Полный машинный договор описан в `core/reverse-patch.md`.

## Основные команды

```bash
python3 scripts/harnessctl.py session-brief <project>
python3 scripts/harnessctl.py doctor <project>
python3 scripts/harnessctl.py wording-check <project> --feature <feature>
python3 scripts/harnessctl.py language-check <project> --feature <feature>
python3 scripts/harnessctl.py requirements-check <project> --feature <feature>
python3 scripts/sync-planning-gantt.py <project> <YYYY-QN>
python3 scripts/harnessctl.py plan-approve <project> <YYYY-QN> --by <owner>
python3 scripts/workspace.py update-code
python3 scripts/reverse_patch.py discover
python3 scripts/reverse_patch.py inspect --artifact-id <artifact-id>
python3 scripts/reverse_patch.py apply --artifact-id <artifact-id>
```

Пользователь не обязан помнить пути. LLM берёт `<project>` из `.analyst-workspace.json` и понимает короткие команды из `templates/workflow/command-catalog.template.md`. Команды `обнови код`, `обнови coda` и `обнови репу с кодом` означают только защищённый `git pull --ff-only`.

## Проверки

Проверка аналитического проекта:

```bash
python3 scripts/harnessctl.py doctor <project>
```

Проверки обвязки:

```bash
python3 -m compileall -q scripts tests
python3 -m unittest discover -s tests -v
git diff --check
```

Проверка структуры отвергает встроенные `.workflow`, `.vscode` и отслеживаемую копию корневого `AGENTS.md`, но разрешает созданную программой местную игнорируемую точку входа.

## Архивы

ZIP создаётся только по прямому требованию пользователя, только в `~/Downloads` и не входит в состояние передачи. Обычная передача выполняется через каталог `requirements-exchange/`.

## Версия

Версия хранится в `VERSION`. Обновление обвязки не устанавливает отслеживаемые служебные файлы в аналитический репозиторий: новые правила применяются из корневого `analyst-harness`, а местная игнорируемая точка входа обновляется повторным `bootstrap`.
