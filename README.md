# analyst-harness

`analyst-harness` - обвязка для долгоживущего продуктового знания: сначала формируется доменная DDD-модель, затем на ней строятся квартальное планирование, требования, прототипы, выполнение работ и финализация релизов.

Репозиторий рассчитан на терминальные инструменты на базе языковых моделей и обычную ручную работу в проекте. Служебные правила и контракт агента живут в `AGENTS.md` и `.workflow/*`, а сам `README.md` нужен как понятная точка входа для человека.

## Как и что здесь устроено

- правила процесса хранятся в репозитории;
- сердцем проекта является доменная модель в логике DDD;
- каноническое текущее состояние в `baseline/current/` отделено от запланированных изменений;
- работа делится на режимы: планирование, требования, прототипирование, исполнение и финализация релиза;
- артефакты группируются по функциональности; срезы остаются аналитическим слоем, а задачи разработки живут рядом с ними;
- прототипы делаются как одиночный `prototype.html` без сборки;
- все ключевые действия описываются короткими командами на русском.

## Сквозной процесс

Обвязка разделяет продуктовое знание, планирование и код, но связывает их проверяемыми пакетами работ. Требования не обязаны лежать в одном репозитории с кодом. Базовая модель такая:

- в репозитории продуктового знания хранится источник истины: текущее состояние, планы, требования, срезы, задачи разработки и фактическое выполнение;
- кодовые репозитории подключаются через `.workflow/code-repos.json`;
- в кодовый репозиторий уходит не копия всего знания, а производный пакет конкретной задачи со ссылками на исходные требования и их хешами;
- разработчик и языковая модель сверяют этот пакет с реальным кодом, тестами и архитектурой;
- если код показывает расхождение с требованиями, сначала корректируются требования и производные артефакты, затем обновляется пакет задачи;
- после реализации факт возвращается в рабочий контур: задачи, проверки, диаграмму фактического выполнения, релизный пакет и затем `baseline/current/`.

### 1. Текущее состояние системы

`baseline/current/` описывает уже реализованную систему:

- доменную модель и словарь;
- текущие бизнес-правила;
- текущие API, данные и интерфейсы;
- принятые решения и ограничения.

Это не план будущих работ. Если новая функциональность ещё не поставлена, она не попадает в `baseline/current/`. После финализации релиза подтверждённое изменение переносится в текущее состояние.

### 2. Планирование

`planning/` хранит входящие заметки, квартальные планы, командирские планы, приоритеты, состав команды, закрытые интервалы и план-факт. Функциональность планируется как законченный пользовательский или системный результат. На неё создаются ролевые плановые истории: AN, BE, FE и QA, если соответствующая роль действительно участвует.

Утверждённые квартальный и командирский планы не меняются. Новая обнаруженная работа после утверждения появляется на диаграмме фактического выполнения как черновик задачи или фактическая задача, чтобы в конце квартала можно было честно сравнить оценку с реальным выполнением.

### 3. Требования и дельта

`features/<feature>/requirements.md` является главным документом требований по функциональности. В нём описывается изменение относительно `baseline/current/`, включая:

- пользовательский и системный результат;
- бизнес-правила;
- изменения данных, API и интерфейсов;
- доработки затронутых соседних функциональностей;
- критерии приёмки и проверки.

Срезы в `features/<feature>/slices/<slice>/` являются производной аналитической декомпозицией. Они помогают проверить целостные пользовательские сценарии, прототипы и покрытие, но не являются обязательной единицей передачи в разработку.

Задачи разработки живут в `features/<feature>/tasks/`, на одном уровне с `slices/`. Одна задача описывает одну роль, один законченный технический результат и одну границу отдельного изменения. Задача может ссылаться на один срез, несколько срезов или только на корневые требования.

### 4. Передача в разработку

Для разработки создаётся пакет задачи:

- `features/<feature>/tasks/index.md` - список задач разработки по функциональности;
- `features/<feature>/tasks/*.md` - отдельные файлы задач для разработчиков и тестировщиков;
- ссылки на корневые требования, связанные срезы, критерии приёмки и проверки;
- подсказки для разбора кода и граница отдельного изменения.

Пакет содержит ссылки на `REQ-*`, критерии приёмки, прототипы и обязательные проверки. Он не становится самостоятельным источником истины и не меняет планирование или план-факт сам по себе: если во время разработки появляется новое правило, ограничение или расхождение, оно возвращается в корневые требования и только потом снова расходится по производным файлам.

### 5. Работа с кодом

Идеальная интеграция с кодом строится без дублирования требований:

- репозиторий продуктового знания остаётся главным источником требований;
- кодовый репозиторий может иметь лёгкую локальную обвязку для приёма пакетов задач, но она хранит только производные материалы;
- каждый пакет задачи фиксирует исходный путь, версию репозитория и хеши требований;
- языковая модель в режиме разработки читает пакет, открывает реальный код, находит затронутые модули, сверяет фактическую реализацию с требованиями и предлагает план реализации;
- если реальный код устроен иначе, чем предполагали требования, языковая модель не маскирует это в плане реализации, а возвращает вопрос или правку в требования;
- после обновления требований пакет задачи пересобирается, чтобы разработка шла по свежему входу.

Практически это может выглядеть так:

```text
repo-product-knowledge/
  baseline/current/
  planning/
  features/<feature>/...

repo-code/
  .workflow/dev-inbox/<task-id>/     # производный пакет задачи, если команда хочет хранить его рядом с кодом
  src/
  tests/
```

Если требования и код лежат в одном монорепозитории, отдельная папка входящих задач не нужна: пакет задачи может ссылаться на соседние файлы напрямую. Если кодовые репозитории отдельные, связь задаётся через `.workflow/code-repos.json`, а пакет задачи должен не копировать всё знание, а указывать источник и контрольные хеши.

### 6. Реализация, проверки и возврат факта

Цикл разработки идёт короткими итерациями:

1. Языковая модель берёт один файл задачи из `features/<feature>/tasks/` и проверяет свежесть требований.
2. Языковая модель сравнивает требования с кодом и уточняет план реализации.
3. Разработчик выполняет подтверждённые задачи с границами отдельного изменения.
4. Проверки запускаются по списку из пакета задачи.
5. Тестировщик сверяет результат с требованиями, прототипом и матрицей покрытия.
6. Пробелы возвращаются в требования, а не остаются только в комментариях к задаче.
7. Завершённая работа отражается на диаграмме фактического выполнения и в релизном пакете.
8. После поставки релиза подтверждённое изменение переносится в `baseline/current/`.

## Кто чем занимается

### Аналитик

- разбирает входящие материалы;
- отделяет текущее поведение от новой дельты;
- выделяет `feature` и `slice`;
- ведет планирование, требования и презентационные прототипы.

### Разработчик

- берет `slice` в работу;
- разбирает реализацию по коду;
- готовит план реализации;
- доводит задачу до ревью.

### Тестировщик

- готовит проверки по `slice`;
- собирает негативные и граничные сценарии;
- сверяет проверки с требованиями;
- фиксирует пробелы и возвраты в требования.

### Служебные режимы

- `planning` - квартальное и командирское планирование;
- `requirements` - требования по фиче и срезам;
- `scope-prototype` - быстрый демонстрационный прототип для уточнения формы решения;
- `delivery-prototype` - точный прототип для передачи в разработку;
- `execution-update` - актуализация факта выполнения;
- `release-finalization` - финализация релиза и перенос результата в текущее состояние.

Утверждённые квартальный и командирский планы являются неизменяемым базовым состоянием планирования. Позднее обнаруженный объём работ отображается через черновики задач реализации и диаграмму фактического выполнения.

## Команды по ролям

Работать здесь удобнее через языковую модель: человек называет команду, а модель сама переключает режим и при необходимости запускает нужные скрипты.

### Аналитик

- `новая фича` - разобрать входные материалы и выделить дельту;
- `занимаемся планированием` - собрать оценки, риски и квартальный план;
- `делаем требования` - оформить требования по фиче;
- `разложи требования на задачи разработки` - подготовить `features/<feature>/tasks/` для передачи разработчикам;
- `делаем презентационный прототип` - собрать общий прототип для согласования;
- `создай прототип среза для фронта` - подготовить прототип передачи в разработку для конкретного среза.

### Разработчик

- `возьми задачу в разработку` - начать работу по одному файлу из `features/<feature>/tasks/`;
- `возьми срез в разработку` - устаревающий вариант, если проект ещё передаёт работу через срез;
- `разбери срез по коду` - посмотреть затронутую реализацию;
- `предложи план реализации` - составить план работ;
- `начни реализацию` - приступить к коду;
- `проверь реализацию среза` - проверить готовый результат;
- `подготовь к ревью` - собрать результат к проверке.

### Тестировщик

- `подготовь проверки по срезу` - собрать тест-дизайн;
- `собери негативные сценарии` - выделить отрицательные и граничные случаи;
- `сверь проверки с требованиями` - проверить покрытие;
- `проверь прототип по срезу` - оценить прототип;
- `проверь реализацию по срезу` - оценить готовую реализацию;
- `зафиксируй найденные пробелы` - вернуть расхождения в требования или план.

## Что лежит в репозитории

- `core/` - постоянные правила и концептуальная модель;
- `modes/` - правила каждого режима;
- `prompts/` - готовые текстовые заготовки под роли и режимы;
- `templates/` - шаблоны для планирования, требований, прототипов и исполнения;
- `scripts/` - скрипты создания структуры и проверки;
- `adapters/cli/` - shell-помощники для переключения режима и старта сессии;
- `adapters/vscodium/` - настройки, задачи и сниппеты для VSCodium;
- `examples/demo-project/` - пример раскладки готового проекта;
- `AGENTS.md` - служебный контракт работы агента в этом репозитории.

## Быстрый старт

### 1. Создайте новый проект

Рекомендуемый путь - использовать скрипт создания структуры:

```bash
bash scripts/scaffold-project.sh /path/to/project
```

Он создает структуру проекта и кладет в нее:

- `.workflow/llm-contract.md`;
- `.workflow/agent-delegation.md`;
- `.workflow/skills-policy.md`;
- `.workflow/tooling-policy.md`;
- `.workflow/context-policy.md`;
- `.workflow/research-policy.md`;
- `.workflow/active-mode.md`;
- `.workflow/modes/*.md`;
- `.workflow/overrides/`;
- `.workflow/command-catalog.md`;
- `.workflow/command-cheatsheet.md`;
- `.workflow/consistency-backlog.md`;
- `.workflow/team.md`;
- `.workflow/tools/`;
- `.workflow/run-state/`;
- `.workflow/templates/`;
- `baseline/current/`;
- `baseline/versions/`;
- `context/`;
- `features/`;
- `planning/intake/`;
- `releases/`;
- `AGENTS.md`.

Если нужен ручной путь без запуска `sh`-скрипта, можно сделать копию репозитория через `git clone`, затем удалить `.git`, переименовать папку и работать уже в этой копии как в новом проекте.

Пример:

```bash
git clone <repo-url> my-project
cd my-project
rm -rf .git
```

Этот способ подходит как ручная заготовка, но после него нужно самому проверить, что в копии есть все нужные каталоги и файлы из списка выше.

### 2. Заполните команду

В новом проекте заполните `.workflow/team.md`:

- кто входит в команду;
- какая у каждого роль;
- какой lane ему назначен;
- какая у него capacity.

Если для проекта нужны собственные формулировки команд, поправьте:

- `.workflow/command-catalog.md`;
- `.workflow/command-cheatsheet.md`.

### 3. Сформируйте доменную модель

До разгона планов и срезов стоит зафиксировать предметную область:

- какие сущности существуют;
- какие у них границы и связи;
- какие бизнес-правила неизменны;
- какие состояния и переходы считаются каноническими;
- что уже находится в `baseline/current/`, а что является новым изменением.

В этой обвязке это центральная точка старта: сначала доменная модель, потом планирование и требования.

Каноническое текущее состояние доменной модели хранится в `baseline/current/domain/`:

- `baseline/current/domain/ubiquitous-language.md`;
- `baseline/current/domain/bounded-contexts.md`;
- `baseline/current/domain/aggregates.md`;
- `baseline/current/domain/business-rules.md`;
- `baseline/current/domain/state-machines/README.md`.

Когда появляется новое изменение, его сначала описывают в функциональности, а затем переносят в текущее состояние после релиза. Для формирования доменной модели удобно опираться на уже существующие требования и команду языковой модели, например:

- `делаем требования` - если нужно собрать или обновить требования по фиче на основе текущих материалов;
- `новая фича` - если сначала надо выделить дельту и только потом расписать доменную модель;
- `занимаемся планированием` - если нужно связать доменную модель с квартальным планом и рисками;
- `делаем требования` + `разложи требования на срезы` - если доменную модель уже надо разнести на проверяемые срезы.

Если пользователь уже знает путь к требованиям системы, можно просить языковую модель сформировать доменную модель прямо по ним:

- `Сформируй доменную модель по требованиям из /path/to/requirements`;
- `Возьми требования из /path/to/project/features/deployments/requirements и собери по ним доменную модель`;
- `Посмотри требования в /path/to/project/baseline/current/requirements и опиши по ним доменную модель текущей системы`;
- `По требованиям из /path/to/project/features/deployments/slices/form-editing/requirements собери доменную модель и перечисли, что должно попасть в baseline/current/domain/`.

### 4. Попросите языковую модель переключить режим

Например:

- `переведи проект в режим планирования`;
- `переведи проект в режим требований`;
- `подготовь старт сессии для проекта`.

Если нужно, языковая модель сама вызовет `switch-mode.sh` или `start-session.sh`.

### 5. Начните работу

Дальше можно просить языковую модель поднимать квартал, функциональности и срезы:

- `создай квартал 2026-Q2`;
- `создай фичу deployments`;
- `создай срез form-editing для фичи deployments`.

При необходимости языковая модель сама вызовет соответствующие скрипты создания структуры из репозитория `analyst-harness`.

## Исполняемая обвязка

Внутренний командный интерфейс не заменяет ролевые команды, а делает правила проверяемыми:

```bash
python .workflow/tools/harnessctl.py doctor .
python .workflow/tools/harnessctl.py session-brief . --feature <feature> --slice <slice>
python .workflow/tools/harnessctl.py run-init . planning --feature <feature>
```

Черновые квартальный и командирский планы генерируются из ролевых историй:

```bash
python .workflow/tools/sync-planning-gantt.py . 2026-Q3
```

После перевода `planning/<quarter>/plan-state.md` в `approved` эти планы больше не пересобираются. Новая фактическая работа появляется на диаграмме фактического выполнения.

### Версия и управляемые файлы

Текущая версия обвязки хранится в `VERSION`. При создании структуры проекта создаётся `.workflow/harness.json`, где фиксируются:

- версия схемы;
- версия и Git-идентификатор обвязки;
- признак изменённого исходного репозитория;
- хеши установленных управляемых файлов;
- список путей, принадлежащих проекту.

Управляемые файлы включают контракты, режимы, внутренние навыки, шаблоны и инструменты. Они обновляются только через `harnessctl upgrade`. Файлы проекта принадлежат конкретному проекту и не перезаписываются обновлением:

- `.workflow/active-mode.md`;
- `.workflow/team.md`;
- `.workflow/code-repos.json`;
- `.workflow/evals/`;
- `.workflow/overrides/`;
- `.workflow/run-state/`;
- `.workflow/runs/`;
- `README.md` проекта.

Проверить различия перед обновлением:

```bash
python /path/to/analyst-harness/scripts/harnessctl.py diff /path/to/project \
  --source /path/to/analyst-harness
```

Выполнить обновление с защитой от конфликтов:

```bash
python /path/to/analyst-harness/scripts/harnessctl.py upgrade /path/to/project \
  --source /path/to/analyst-harness --apply
```

Если управляемый файл был изменён локально, команда обновления сообщает `CONFLICT` и ничего не перезаписывает. Проектное отличие нужно либо перенести в обвязку, либо оформить в `.workflow/overrides/`.

### Безопасное создание структуры

Команды создания структуры не перезаписывают существующие знания по умолчанию:

```bash
bash scripts/scaffold-project.sh /path/to/project
bash scripts/scaffold-project.sh /path/to/project --merge
bash scripts/scaffold-feature.sh /path/to/project feature-slug --merge
bash scripts/scaffold-slice.sh /path/to/project feature-slug slice-slug --merge
```

- обычный запуск требует пустой целевой каталог;
- `--merge` добавляет только отсутствующие файлы обвязки;
- `--force` является явной операцией перезаписи файлов создаваемой структуры;
- слияние с проектом не создаёт файлы-заглушки внутри существующих `baseline/`, `features/`, `planning/` и `context/`.

## Подробная модель планирования

### Функциональность и плановые истории

Функциональность является законченной пользовательской или системной ценностью квартала. Плановая история — не функциональный срез, а ролевой поток работ внутри функциональности.

На одну функциональность допускается максимум четыре плановые истории:

- `STORY-<FEATURE>-AN`;
- `STORY-<FEATURE>-BE`;
- `STORY-<FEATURE>-FE`;
- `STORY-<FEATURE>-QA`.

Если работа конкретной роли не нужна, соответствующая история отсутствует. Функциональная декомпозиция выполняется позднее в режиме требований через срезы.

### Оценка и длительность

Для каждой ролевой истории сохраняются:

- опорная оценка аналитика;
- оценка команды;
- явно согласованная оценка;
- допустимый параллелизм;
- коэффициент эффективности;
- зависимости;
- ограничение `not before`.

Итоговая оценка не вычисляется усреднением. Она считается принятой только после явного согласования.

Длительность рассчитывается так:

```text
ceil(agreed effort / effective parallel capacity)
```

Коэффициенты по умолчанию:

- `AN = 0.80`;
- `BE = 0.70`;
- `FE = 0.65`;
- `QA = 0.80`.

Коэффициент роли может быть переопределён в истории, а персональный коэффициент — в `.workflow/team.md`.

### Ресурсы и приоритет

- `gantt/order.txt` хранит приоритет фич сверху вниз;
- готовая работа более приоритетной фичи первой получает подходящие ресурсы;
- свободная роль может перейти к следующей фиче, пока в верхней фиче для неё нет готовой работы;
- нижняя фича не должна задерживать ставшую доступной работу верхней;
- автоматическое прерывание уже начатой работы не выполняется;
- загрузка ресурса не превышает 100%;
- отпуска и другие закрытые интервалы задаются в `.workflow/team.md`;
- плановая история может использовать несколько ресурсов до `max_parallelism`;
- фактическая задача всегда назначается одному человеку.

Стандартные зависимости: `AN -> BE`, `AN -> FE`, `BE + FE -> QA`. FE стартует не раньше трёх открытых рабочих дней после старта BE. Если BE отсутствует, FE стартует после AN либо в первое доступное окно.

### Квартальный и командирский планы

Квартальный план строится по согласованным оценкам без командирского резерва. Командирский план использует тот же объём работ, порядок и зависимости, но добавляет резерв риска:

- минимум 20%;
- 30% для высокого риска или внешней зависимости;
- 40% для нескольких высоких рисков, новой интеграции или неясной модели данных;
- 50% для критической неопределённости или неподтверждённой архитектуры;
- более 50% требует ручного решения.

Резерв влияет на длительности и даты командирского плана, но не показывается руководству отдельной полосой.

### Утверждение и неизменяемость

План имеет состояния `draft` и `approved`. Только владелец проекта утверждает план:

```bash
python .workflow/tools/harnessctl.py plan-approve . 2026-Q3 --by <owner>
```

При утверждении сохраняются хеши основных PlantUML-файлов, включаемых файлов функциональностей и базовых колонок карт фактического выполнения. После этого:

- квартальный и командирский планы не пересобираются;
- базовые даты начала и длительности в картах фактического выполнения не меняются;
- новый объём работ появляется как черновики задач реализации или фактические задачи;
- диаграмма фактического выполнения остаётся единственным изменяемым представлением реального положения дел;
- `validate-planning.py` обнаруживает любую правку утверждённого базового плана.

### Ретроспектива

После квартала:

```bash
python .workflow/tools/calibrate-planning.py . 2026-Q3
```

Инструмент сравнивает оценку роли с длительностью фактических задач и предлагает новые значения коэффициента эффективности и риска. Предложения применяются только к будущим черновым планам и никогда не переписывают историю.

## Требования, влияния и задачи разработки

### Язык требований

Описательная часть требований пишется на русском языке. Английская форма допускается только там, где перевод нарушит точность:

- код и команды;
- пути к файлам;
- методы и поля API;
- таблицы и поля базы данных;
- значения перечислений и статусов протокола;
- закреплённые названия внешних систем;
- общепринятые технические сокращения вроде HTTP, JSON, SQL, API, FE, BE и QA.

В остальных случаях используются русские формулировки: «объём работ» вместо scope, «текущее состояние» вместо baseline, «срез» вместо slice, «передача в разработку» вместо handoff, «влияние» вместо impact.

Проверка изменённых требований:

```bash
python .workflow/tools/harnessctl.py language-check . --feature <feature>
```

Полный аудит всех требований выполняется только явно:

```bash
python .workflow/tools/harnessctl.py language-check . --all
```

Языковой контроль входит в обязательный второй проход вместе с поиском смысловых хвостов.

Корневые требования являются главным авторским источником. Карточки срезов, пакеты FE/BE, задачи разработки, планы реализации и покрытие QA являются производными.

После изменения требований выполняются два прохода:

1. Обновление корневых требований и всех непосредственно производных срезов.
2. Поиск устаревших маршрутов API, полей, статусов, ролей, терминов, прототипов и соседних правил.

Локальный необъяснённый хвост блокирует завершение. Работа на стыке режимов может быть отложена только конкретной записью в журнале несогласованностей.

Обязательные изменения соседних функциональностей включаются в объём работ инициирующей функциональности и раздел `Доработки затронутых фич`. Каждая строка должна быть покрыта `REQ-*`, задачей разработки и проверкой либо иметь явное `not applicable` с причиной.

Задачи разработки создаются по команде `разложи требования на задачи разработки`:

- одна роль;
- один смыслово законченный результат;
- граница отдельного изменения или PR;
- ссылки на `REQ-*`/`AC-*`;
- ссылки на связанные срезы, если они нужны;
- зависимость и обязательная проверка;
- целевой размер BE/FE/QA 1–3 дня;
- максимум BE 5 дней, FE/QA 10 дней;
- для AN размер не ограничивается.

## Исполнительские циклы

Состояние каждого цикла хранится в `.workflow/runs/<run-id>/run.json`. Общая петля выполнения:

```text
сориентироваться -> спланировать -> выполнить ограниченное действие -> проверить
                 -> независимо пересмотреть -> зафиксировать контрольную точку -> продолжить/завершить/эскалировать
```

Создание циклов:

```bash
python .workflow/tools/harnessctl.py run-init . planning --feature <feature>
python .workflow/tools/harnessctl.py run-init . requirements --feature <feature>
python .workflow/tools/harnessctl.py run-init . implementation --feature <feature> --slice <slice> --role BE
python .workflow/tools/harnessctl.py run-init . qa --feature <feature> --slice <slice> --role QA
```

`implementation` и `qa` используют `.workflow/code-repos.json`. Цикл сохраняет хеши входных требований. Если они меняются во время работы, `run-verify` возвращает ошибку свежести и требует обновить рабочий пакет.

Проверка задаётся массивом аргументов без интерпретации командной оболочкой:

```json
{
  "name": "targeted tests",
  "argv": ["pytest", "tests/test_slice.py"],
  "cwd": "."
}
```

Запуск:

```bash
python .workflow/tools/harnessctl.py run-verify .workflow/runs/<run-id>/run.json
```

Повторяющаяся ошибка после заданного лимита переводит цикл в `escalated`.

## Диагностика и проверки

`harnessctl doctor` объединяет проверки структуры, процесса, ссылок, контекста, планирования и трассировки. `--strict` переводит предупреждения по контексту и трассировке в ошибки.

Синтетические проверки контролируют чистое создание проекта, несоответствие режима, защиту от разрушительного создания структуры и подмену утверждённого плана:

```bash
python scripts/evaluate-harness.py
```

Проектные эталонные сценарии живут в `.workflow/evals/golden-scenarios.json`:

```bash
python .workflow/tools/evaluate-harness.py .
```

Они предназначены для низкодрейфовых доменных инвариантов, а не для копирования полного набора требований в eval-конфигурацию.

## Типовой рабочий цикл

1. `новая фича` - разобрать исходные материалы и выделить дельту.
2. `занимаемся планированием` - подготовить оценки, риски и квартальный план.
3. `делаем требования` - оформить требования по фиче.
4. `делаем презентационный прототип` - собрать прототип для согласования.
5. `делаем прототип для разработки` - подготовить прототип передачи в разработку для среза.
6. `разложи требования на задачи разработки` - подготовить файлы задач в `features/<feature>/tasks/`.
7. `возьми задачу в разработку` - начать реализацию одной задачи.
8. `подготовь проверки по срезу` - подготовить тест-дизайн и покрытие.
9. `финализируем релиз` - зафиксировать результат и перенести его в текущее состояние.

## Как читать структуру проекта

- `baseline/current/` - текущее каноническое состояние системы;
- `baseline/versions/` - предыдущие версии текущего состояния;
- `features/` - папки по отдельным функциональностям;
- `planning/` - квартальные планы и входящие заметки;
- `planning/intake/` - заметки предварительного разбора перед созданием структуры новой функциональности;
- `context/` - исходные материалы и описания текущей системы;
- `releases/` - неизменяемые релизные пакеты перед переносом в текущее состояние.

## Коротко о том, как не запутаться

- сначала создается или копируется проект;
- потом фиксируется команда и активный режим;
- затем функциональность проходит через планирование, требования, прототипы, исполнение и релиз;
- `baseline/current/` обновляется только после финализации релиза;
- в спорных случаях источником истины остается markdown в репозитории.
