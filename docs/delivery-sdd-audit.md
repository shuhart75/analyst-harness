# Аудит передачи поставок и разработческой SDD

Дата: 5 октября 2026 года.

Проверенные исходные версии: `analyst-harness` —
`b6afa68f56eb65ccbc33ec24ef8d1a2f37cac77b`, `coda-analyst-harness` —
`a33fa97dba4c7ccce24741d4dd0c4be8fd88d9c6`. Исправления подготовлены поверх них
в локальных ветках `codex/delivery-sdd-audit`, без коммита и отправки.

## Вывод

Переход на квартальные поставки уже отражён в транспорте: схема 4 связывает
бизнес-фичу, поставку, квартал и транспортный ключ с аудитом и редакцией.
Полная замена механизма обмена на OpenSpec Store не требуется. Нужны одинаковые
проверки идентичности при чтении и принятии возвратов, законченный порядок
разработческой работы и отдельный вход для GigaCode.

Проверены обе обвязки: `analyst-harness` и `coda-analyst-harness`. Основание —
текущие договоры, скрипты, шаблоны и интеграционные тесты. Рабочие требования,
опубликованные пакеты и продуктовый код этим изменением не обновляются.
Зарегистрированная в обычной обвязке роль code пропущена; запуск GigaCode и
версия SDD в реальной среде разработчиков этим аудитом не проверены.

## Модель после перехода

| Сущность | Смысл и граница |
|---|---|
| `feature_id` | Долгоживущая бизнес-возможность, её паспорт не передаётся как контракт поставки |
| `delivery_key`, `delivery_id`, `quarter` | Точный поток квартальной поставки; `manifest.feature` сохраняет транспортный ключ |
| `stage_id` / `stage_revision` | Согласованный бизнес-объём и исправления внутри действующего договора этапов |
| `revision` + SHA-256 | Неизменяемый переданный вход в пределах одного потока поставки |
| Локальный change SDD | Техническое изменение разработки; одной редакции могут соответствовать несколько changes |
| `return_id` | Конкретный возврат редакции, не переносимый в другую поставку |

Поставка, этап и технический change не являются синонимами. Действующий запрет
параллельных незакрытых этапов одной бизнес-фичи сохранён. Упрощение этой модели
или разрешение параллельных поставок требует отдельного предметного решения,
а не переименования параметра `feature` в CLI.

| Приоритет | Наблюдение | Результат |
|---|---|---|

| P2 | Не определены общий владелец возвратов и проверка нескольких кодовых репозиториев | Зафиксированы один канонический exchange, консолидатор, repository/commit/change/task/REQ и общая проверка |
| P2 | Аналитический skill GigaCode не был разработческим входом | В coda добавлены шаблоны GIGACODE и необязательной команды delivery-sdd, подключаемые разработчиком |

Изменения нейтрального договора и двух проверок внесены в обе обвязки.
Нативные файлы и изменение skill находятся только в coda-варианте.
Подготовка по-прежнему записывает в коде только `requirements-exchange/**`
через отдельную review-ветку, сохраняя обычный code checkout.
Корневой `GIGACODE.md` и `.gigacode/` кодового репозитория автоматически не меняются.

## Обработка релиза, доменная модель и очистка обмена

По согласованному дополнению триггером служит обработка подтверждённо
внедрённого релиза. Проверяются полный состав, результаты всех поставок,
подробные решения по REQ и остаток. В подготовке baseline обязательны
шесть аспектов доменной модели: сущности, связи, правила, жизненные циклы,
процессы и диаграммы. Каждый получает updated/unchanged с основанием;
проверка связана с точным исходным baseline и кандидатом. Отсутствующая
или изменённая проверка блокирует продвижение. Семантическую актуальность
модели проверяет аналитик; наличие заполненных полей её само по себе не доказывает.

После продвижения baseline полностью завершённые поставки архивируются
в `releases/<release-id>/exchange-archive/<delivery-key>/` аналитики.
Все редакции и возвраты сохраняются побайтно вместе с прежними return_id;
сопровождающие договоры находятся в соседнем `exchange-contracts/<delivery-key>/`.
Решение о завершении связано с packet_hash всего проверенного пакета.
Частичные поставки остаются в рабочем обмене.

Очистка разрешена только после проверки принятого архива и baseline в свежем
analytics/main. Для code инструмент создаёт отдельную review-ветку точного
удаления; обычный checkout не меняется. Для analytics удаление готовится
в рабочей ветке. В обоих случаях завершение подтверждается повторной проверкой
после принятия удаления. Незавершённая очистка видна в baseline scan;
повторное продвижение baseline для неё не нужно. Архив доступен через
`requirements-exchange.py scan --archived`.

Проверки включают настоящий временный Git remote и полный цикл code:
архив → принятие analytics/main → ветка удаления → человеческое слияние →
подтверждение завершения. Проверены подмена пакета, новые возвраты, симлинки,
непринятые побочные коммиты в cleanup-ветке и повтор после продвижения main.
Для code требуется сохранение точного cleanup-коммита в истории;
squash или удаление review-ветки до проверки оставляют операцию заблокированной
для разбора. Реальные пакеты и baseline в рамках аудита не менялись.

## Сохранившиеся ограничения реализации

- Транспорт поддерживает одного получателя роли `code` либо резервный `analytics`.
  Несколько code-репозиториев работают через согласованный общий exchange;
  независимых квитанций и автоматического слияния их результатов нет.
- `completed` проверяется структурно по файлам и наличию REQ в summary.
  Это не семантическая валидация задач, контуров, доказательств и сценариев.
  Обязательны содержательная сверка получателя и подробное аналитическое `reviewed`.
- Обычный `scan` выбирает активную редакцию; поздний возврат старой требует
  отдельного разбора. Копировать его в новую редакцию запрещено.
- Вложенный `GIGACODE.md` нельзя считать автоматически загруженным. Получатель
  подключает его из корневых правил и проверяет запросом только на сверку.
- Установка OpenSpec Store, миграция существующего `openspec-de-*`, реальное
  подключение разработческих репозиториев и пробный запуск GigaCode не выполнены.
  Их нельзя объявить проверенными по PDF или локальным unit-тестам harness.

## Проверка перед использованием

Целевые regression-тесты проверяют отказ принимать чужую поставку без записи
состояния, успешную обработку корректного возврата и продолжение scan при
неизвестном потоке. Тесты публикации проверяют состав приёмного каталога,
неизменность обычного code checkout и отсутствие записи вне exchange.
Полная регрессия выполняется отдельно для каждого варианта harness.

Результат проверки подготовленного изменения:

| Проверка | Результат |
|---|---|
| Полная регрессия analyst-harness, включая релизную архивацию | 701 тест, OK, один пропуск |
| Полная регрессия coda-analyst-harness, включая релизную архивацию | 732 теста, OK, один пропуск |
| `test_baseline_releases` | 41 тест в каждом варианте, OK |
| `test_release_exchange` | 17 тестов в каждом варианте, OK |
| `test_exchange_cleanup` | 12 тестов в каждом варианте, OK |
| `test_delivery_exchange` | 15 тестов в каждом варианте, OK |
| `test_requirements_exchange` | 30 тестов в каждом варианте, OK |
| `harnessctl doctor` для текущей аналитики | OK; предупреждения о legacy-оценках и отсутствующей единице оценки |
| Проверки ссылок и контекста текущей аналитики | OK |
| Формат skills coda-delivery и coda-release, общий договор двух вариантов, `git diff --check` | OK |

В обоих полных прогонах пропущен один тест отрисовки Ганта: не задан
`PLANTUML_JAR`. Изменение не затрагивает генерацию или отрисовку Ганта.
Локальные тесты не доказывают загрузку правил в реальном GigaCode или доступность
команд Store у разработчиков.

У разработчиков первый запрос должен быть только на сверку: точные ключ/редакция,
опубликованный вход, прочитанные договоры, доступный вариант SDD, карта репозиториев
и границы записи. Затем на согласованной работе проверяются компонентные тесты
и общий сценарий; отсутствие общей среды отражается как непроверенный результат.
